ReviveCheck

Release attestation middleware for Portaldot V3.

Approvals that contracts enforce: a release owner commits a sealed report's hash to the ReleaseRegistry, reviewers approve that exact hash, and any V3 contract reads it through the ReviveCheckGuard library.

Evidence on-chain: the sealed report itself is stored through the native Remark module and retrieved from any node by its hashes.

A decision a maintainer can inspect: a policy evaluation against fresh finalized reads, with every check, reason and next action.

The maintainer's problem

A Portaldot wallet or DEX token-list maintainer publishes entries that wallets and DEX allow-lists read.

Where the approval lives today: a JSON token list, a spreadsheet or a chat thread. No contract can read it.

What was approved: "the release", with no record of what the reviewer saw.

The evidence: a screenshot, or a link whose content can change.

Checking the chain: someone opens an explorer and reads one interface.

Nothing tells them when it stopped holding.

The promise

Publish entries supported by the exact approved evidence.

Understand why an entry is no longer eligible.

Restore eligibility through a new review and explicit binding.

A policy states what a business action needs beyond the contract's answer: the right network and genesis, the subject, the plan fingerprint, supported runtimes, evidence age, an explicit trusted reviewer set, the consumer's listing and the stored report, each checked against fresh finalized reads.

The evaluation returns valid, recheck-required, expired or unknown. Only valid enables; an unavailable read is unknown, never a pass.

A new report needs a new approval and an explicit rebinding; history is kept.

The decision screen

The Catalog decision page, #/app/catalog: the published entry against the approved report, the on-chain approval, the listing, the policy verdict with its reasons, evidence age against the policy clock, the checkpoints, the next action and the binding history.

Three facts are kept apart: the on-chain approval (the registry's decision), the recorded execution (finalized receipts, each linked to its block) and the current policy eligibility (an evaluation at a checkpoint and time).

Evaluate now runs the same evaluator the CLI and the Token Catalog use, in the browser, against the current finalized block. No wallet; nothing is signed.

Recorded evaluation 9dfc49fa… at #187279: valid, 35 checks; the published entry equals the approved report 1faef921… field by field.

Validity is point-in-time: evaluate again before each use.

Reuse

One implementation, lib/service.js, behind the browser, the MCP server, REST, the JavaScript module and the CLI: thirteen read-only tools. Writes are dry-run, then signed in the user's own wallet.

The package declares nineteen exports specifiers (., ./policy, ./current, ./decision, ./catalog-release, ./health and more), a files whitelist and three bin commands: revivecheck, revivecheck-mcp and revivecheck-catalog, the release gate that writes a versioned catalog release only when the entry is permitted.

A packed artifact, revivecheck-0.5.0.tgz (SHA-256 d8184943…, 53 files), produced with npm pack from commit e105dfe and verified from an empty install, including the shipped release-gate starter; a second consumer installs it from the tarball with npm ci.

That consumer is a DEX allow-list in a separate repository with its own policy (hash 795942d6…), six offline scenarios, 19 passing tests and a CI workflow that has not yet run; its live runs on 2026-10-25 allowed pUSD (valid at #191199) and prepared catalog release 1 at #192724, which a separate reader consumed. The repository is local and unpublished.

Author-run: portability, not adoption. No builder outside the project has installed or configured ReviveCheck; an external builder running it is the next gate.
