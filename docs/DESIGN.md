# Design System: ReviveCheck

## Overview

**Creative North Star: "The Registry Desk"**

ReviveCheck sells on-chain release approvals as permissions a contract enforces, and the site is built like a commercial infrastructure product: a marketing landing that opens into a live dashboard. The ground is cool paper, never white; everything that carries content is a white card on a 1px hairline, so the page reads as a desk of records rather than a document. The hero does not describe the product, it shows the recorded approval: a card with the approval block as a large rolling numeral, a transaction-status card whose steps check off on load, and a "Listing allowed" toast overlapping its corner, all over a faint masked grid and two soft Portaldot glows. The app keeps the same desk at operating restraint: a 60px bar, a sidebar, cards, tiles, and the live finalized head rolling in the overview's hero card.

Color is scarce and means something. One indigo does the action and the live number: the primary pill button, links and chain references, the counters in the stats band, the current nav item, the "App" tag. Three status triads (green pass, red fail, amber hold) appear as a dot and a soft tint, or as status-colored text, never as a block. One near-black band holds what is enforced: the rules band on the landing, the lifecycle tab panel, the "Run it with your own wallet" card, and the dark readback panels. The Portaldot violet-to-azure gradient is the co-brand and the live signal: hero glows, the contract dots in the sidebar, the running stage's border, the current transaction pill, the indeterminate sweep, and the closing band.

Motion is one fast-out settle ease applied sparingly: blocks rise 14px as they enter, every chain number rolls in as an odometer, the hero's status steps fire in sequence, the lifecycle tabber advances under a linear progress rule, and mega-menus scale-fade in. Under `prefers-reduced-motion` every animation and transition is removed and the finished state is rendered at once. The world is light only (`color-scheme: light`, `theme-color #f5f6f8`); selection, caret, scrollbar, focus ring and the native select chevron are themed to match.

**Key Characteristics:**
- Cool paper ground with white hairline cards; near-black ink and four grays; two hairline weights.
- Geist on its weight axis for every text role (650 display, 600 titles, 550 UI, 400 body); Geist Mono with tabular figures only for chain data and code.
- Indigo pill buttons (40/32/48px) with a soft indigo glow; white hairline pills as the secondary.
- Status is a dot plus a soft tint; the running state breathes.
- One dark band for the rules; the Portaldot gradient only as glows, co-brand and live progress, plus the closing band.
- Every chain number is a rolling odometer; cards rise 14px on entry; nothing moves under reduced motion.

## Colors

A cool-paper developer palette: one gray ground, white surfaces and three hairlines, near-black ink with four grays, one indigo, three status triads, one dark band, and the Portaldot pair held for the co-brand and live progress.

### Primary
- **Indigo** (accent): The primary button fill, text links, chain and hash links, the focus outline, the caret, the running badge, the indexed network dot, the stats band's counters, the approval card's meter, the current transaction dot, the selected lifecycle tab's number, the active sidebar icon. Selection is indigo at 18% over white; the input focus ring is indigo at 16%.
- **Deep Indigo** (accent-hover): Primary button and link hover, the "Why it matters" head, the highlighted mark inside code blocks, the hover color of brand names and mega-menu footers, and the primary's label on the gradient closing band.
- **Indigo Wash** (accent-soft): The running badge, the "App" tag, the current sidebar item, the product lane tag, the "stored" kind chip, the module strip's brand cell, the "Why it matters" panel, and the 4px halo around the current transaction dot.
- **Indigo Ink** (accent-ink): Text on indigo wash: the "App" tag, the current sidebar item, the product lane tag, the "stored" chip, the brand cell's small label.

### Secondary

**The Paper-And-Card Rule.** The page ground is cool paper and content lives on white hairline cards. A white page ground, or a card drawn directly on another card without a hairline, breaks the desk.

**The Indigo-Leads Rule.** Indigo means the action or the live number: the one primary button in a view, links and chain references, counters, the current item, the running state. Its washes mark "current" or "product" and nothing else; indigo never fills a heading, a card body or a status.

**The One-Dark-Band Rule.** Near-black surfaces hold what is enforced or recorded: the rules band, the lifecycle panel, the wallet card and the readback panel. There is no dark theme and no dark section outside these.

**The Gradient-Is-Live Rule.** The Portaldot gradient reads as soft glows behind the hero and the app's hero card, as the co-brand dot, on live progress (the running stage, the current transaction pill, the sweep), and as the closing band. A static card, heading or button never carries it.

**The Dot-And-Tint Rule.** Status is a 6px dot plus a soft tint badge with a matching line, or status-colored text. No status ever fills a solid block.

### Do:
- **Do** keep the ground cool paper and every content surface a white card on a 1px hairline; use the four text grays (ink, ink-2, ink-3, ink-4) and the three hairlines (line, line-strong, line-hover) for every neutral need.
- **Do** set every hash, address, block link, runtime version, command and code sample in Geist Mono with tabular figures, link chain values to the official explorer in indigo, and set a card's headline block number as a large Geist numeral that rolls in as an odometer.
- **Do** express status as a dot plus a soft tint badge (pass, fail, hold, run, quiet), a kind chip, or status-colored text.
- **Do** use pills for every button and chip, 8px for fields, 10px for tracks and sidebar links, 12px for code and nodes, 16px for cards, 18px for the hero's recorded cards, 20px for the dark panel and 24px for the dark band.
- **Do** keep the raised shadow for the hero's recorded cards, product visuals, mega-menus, dialogs and toasts; working cards and tiles sit on the hairline shadow.
- **Do** put the Portaldot gradient only on glows, the co-brand dot, live progress and the closing band, and show the official Portaldot mark unaltered, only as "Built on … Portaldot V3", with clear space of at least a quarter of its height.
- **Do** focus with the 2px indigo outline at a 2px offset (white on the band and the gradient; inputs take an indigo border plus a 16% ring), and remove every animation and transition under `prefers-reduced-motion` while rendering the finished state.

### Don't:
- **Don't** set the page ground white, place a card on a card without a hairline, or alternate page-wide bands; the stats band and the closing band are the only full-width tints.
- **Don't** fill a heading, a card body or a status with indigo, or use its wash for anything but "current" and "product"; one indigo primary per view.

## Interface Evidence Boundaries

These product constraints decide what the interface may claim. They carry over from the v0.2 design unchanged in substance, updated for the current routes: the lifecycle runs at `#/app/run` ("Run the lifecycle"), the reviewer at `#/review` inside the app shell, the data pages at `#/app/releases`, `#/app/tokens`, `#/app/evidence` and `#/app/activity`, and the local workbench at `#/app/workbench` on loopback only. Product truth lives in `docs/PRODUCT.md`.

### Four states, no combined approval badge

| State | Meaning | What cannot change it |
| --- | --- | --- |
| Verification | Outcome of the saved checks; rehearsal is a sample | Sharing or a reviewer opinion |
| Publishing | Local share preparation | Copying a link does not prove hosting or delivery |
| Review | Opinions attached to this exact report hash | A new run cannot inherit those opinions |
| Freshness | Whether current local settings or later saved runtime observations differ | A historical pass does not guarantee the current chain is unchanged |

Each state gets its own badge or banner; they are never merged into one approval mark. Next-step guidance explains the first unresolved check or stale context. A failed report can be accepted as an accurate failed observation; the failure remains visible. A new release, deployment, plan or detected runtime change calls for a new run, not a rewrite of history. The hero's approval stack and the app's recorded run show the recorded lifecycle as it happened, including the refused V3 Live promotion; they are not approval marks.

Comparison uses precise language. Correcting the expected chain is a configuration correction. Different deployments require the same explicit logical identity and assertion plan. Changed assertions, caller or asset holder require a new baseline. Runtime and fixture changes receive context-changed labels rather than a repair count. Even an improved check does not establish its cause.

### Static recipient experience

The reviewer at `#/review` verifies report JSON with browser Web Crypto, reads the same check ledger and saved plan, and creates an accepted/changes-requested receipt. The receipt binds one report hash and is downloaded for the owner to import. Reviewer identity in a receipt is explicitly self-declared. There is no login, backend or official authority. A reviewer may optionally record the decision as a `system.remark_with_event` signed with their own wallet extension. That authenticates an account, not a person. Imported receipts can be checked against the selected report.

Reports travel in one of three ways:

1. A gzip/base64url fragment contains the report and is decoded in the recipient's browser. The fragment payload is not sent to the static host.
2. A selected published reference report is fetched from the static site and must match its requested fingerprint.
3. A fingerprint-bound viewer opens with an explicit request for the matching JSON file. This is the fallback for long links or QR payloads.

The current limits are 512 KiB expanded report data, a 32,000-character complete link, and a conservative 1,800-character self-contained QR link. A hash-only QR does not contain a report and must say that JSON import is required. The local API and workspace database are never the sharing endpoint. Report metadata remains public to anyone who receives it; compression is not encryption.

A video or selected reference report is not proof that the viewer reproduced a live run or that a real external reviewer participated.

### Evidence contract behind the interface

A sealed run binds the acceptance plan, declared source revision, deployment and observed code fingerprint where available, runtime fingerprint, and finalized native/EVM checkpoint. Dynamic sharing, review and freshness data remain outside that sealed payload. Original JSON is the integrity artifact; HTML is a readable rendering with the companion JSON boundary stated explicitly.

Hash matching means the content is unchanged. It does not authenticate the source of RPC responses, the developer, the reviewer, or a declared source revision. A passing asset profile covers read parity of an existing public asset; local ReleaseGate EVM execution covers local bytecode behavior. These boundaries belong beside the relevant action and result, not only in a footer. Reads in the app need no wallet and spend nothing; every write is dry-run, then signed in the visitor's own wallet with the visitor's own tPOT; the site holds no key.
